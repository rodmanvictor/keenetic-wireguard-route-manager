# Архитектура проекта

Проект разделён по ответственности. Рабочий код не лежит в корне репозитория.

```text
keenetic-router/
├── src/keenetic_router/       Python-пакет
│   ├── core/router.py          подключение к KeeneticOS и операции с маршрутами
│   └── apps/                  пользовательские приложения
│       ├── tui.py             терминальное меню packetech tui
│       ├── cli.py             команды packetech
│       ├── launcher.py        выбор GUI, CLI или TUI
│       ├── importer.py        команда kwimport
│       └── desktop.py         desktop-интерфейс
├── integrations/chrome/       Chrome-расширение и Native Messaging host
├── integrations/systemd/      шаблоны локального таймера обновления
├── tools/                     вспомогательные утилиты, не являющиеся основным UI
├── examples/                  примеры входных файлов
├── scripts/                   установка, сборка и проверки проекта
├── docs/                      устойчивая документация
├── tests/                     автоматические тесты
└── var/                       локальные отчёты и SQLite-базы, вне Git
```

## Ядро

`src/keenetic_router/core/router.py` — единственное место для низкоуровневых Telnet/SSH-команд, поиска WireGuard-интерфейсов, DNS-разрешения и работы с маршрутами. `core/profiles.py` хранит один профиль роутера вместе с паролем в пользовательском JSON с правами `600`, `core/onboarding.py` диагностирует транспорт и компоненты, `core/wireguard.py` проверяет, импортирует и управляет `.conf`/QR-профилями. Все интерфейсы используют эти модули, а не реализуют собственное подключение.

Рабочий транспорт выбирается не настройкой наугад, а реальным входом: сначала SSH, затем Telnet с попыткой выполнить `service ssh`. Telnet остаётся аварийным режимом; WireGuard-ключи через него не передаются.

`src/keenetic_router/services/` содержит SQLite-реестр доменов, обновление DNS-маршрутов и обратную инвентаризацию. A и AAAA превращаются в точные IPv4 `/32` и IPv6 `/128`; маршрут может иметь несколько независимых источников, поэтому общий IP не теряет маршрут при отключении одного сервиса.

## Интерфейсы

- `packetech` без аргументов запускает графическое приложение.
- `packetech status`, `add`, `sync` и другие подкоманды запускают CLI.
- `packetech tui` запускает интерактивное терминальное меню.
- `packetech-cli` предоставляет CLI/TUI отдельно от графической части.
- `kwimport` импортирует файлы в формате Windows `route add`.

Запускаторы в `bin/` сохраняют совместимость с привычными командами и передают выполнение в Python-пакет из `src/`.

## Интеграции и данные

Chrome-расширение не содержит логики управления роутером: оно передает запрос отдельному native host, а тот загружает сохраненный профиль PackeTech и использует общее ядро. Мастер в desktop-приложении копирует расширение в постоянную пользовательскую папку, регистрирует native host и открывает Chrome; ручным остается только обязательное подтверждение распакованного расширения. В `var/` хранится SQLite-база автоматического обновления маршрутов; папка специально исключена из Git. На Linux обновление раз в шесть часов запускает user-timer systemd, на Windows — локальная задача `PackeTech route sync`, на macOS — LaunchAgent.
